## 三、关键设计决策验证

### 3.1 数据模型设计 ✅

```python
admin_users (统一用户表)
├── role = 'admin'    → 系统管理员
├── role = 'doctor'   → 真实医生（新增）
├── role = 'editor'   → 内容编辑
├── role = 'reviewer' → 审核员
├── doctor_attributes JSON → 医生专属信息
└── department_id → FK departments.id（关联科室）
```

**评估**：
- ✅ 扩展性强，添加新角色只需增加 `role` 枚举值
- ✅ `doctor_attributes` JSON 字段灵活存储医生信息
- ✅ `department_id` 科室关联符合实际业务逻辑

### 3.2 医生与 AI 分身关联 ✅

```python
# 医生通过科室关联 AI 分身
admin_users.department_id → departments.id ← doctors.department_id
```

**查询逻辑**：
```python
# 获取本科室的 AI 分身
ai_doctors = db.query(Doctor).filter(
    Doctor.department_id == current_doctor.department_id
).all()

# 获取这些 AI 分身接待的患者
patients = db.query(User).join(ConsultationSession).filter(
    ConsultationSession.doctor_id.in_([d.id for d in ai_doctors])
).distinct().all()
```

**评估**：
- ✅ 利用现有的 `department_id` 字段，无需新建关联表
- ✅ 符合实际：皮肤科医生查看皮肤科 AI 分身的患者
- ⚠️ 限制：如果医生跨科室，需要额外处理

### 3.3 路由设计 ✅

| 路由 | 前缀 | 认证 | 说明 |
|------|------|------|------|
| 患者医嘱 | `/medical-orders` | 患者 | 患者为自己创建 |

**评估**：
- ✅ 路由前缀清晰分离
- ✅ 认证依赖明确（患者/医生/管理员）
- ✅ 与现有系统无冲突

## 七、待确认问题

在开始实施前，建议确认以下问题：

1. **科室关联方式**：医生是否只看本科室的 AI 分身患者？

   - 否 → 需要 `managed_doctor_ids` 或关联表

2. **医嘱创建权限**：
   - 医生是否可以为任何患者创建医嘱？
   - 还是需要先建立"医患关系"？

3. **测试账号**：
   - 是否需要创建专门的测试医生账号？
   - 测试医生属于哪个科室？
